## Slide 1: Maze Arena (35 s)

[Baya Chaabene] Hello, we are Baya Chaabene, Mohamed Aziz Souissi, Yahia Mahfoudh and Yassine Friaa. This is Maze Arena: a multiplayer maze game for up to three players. We built the same game twice, once over TCP and once over UDP, so that we could compare the two protocols on exactly the same game. In the next twenty minutes we explain how both versions work, we show them live on four laptops, and we show what we measured.


## Slide 2: Our 20 minutes (25 s)

[Baya Chaabene] Our question is simple: which transport suits a real-time multiplayer game, and why? First we present the game and our design, then the TCP version and the UDP version. Then the most important part: a live demo on four laptops, with four short games that each prove something. We finish with our measurements and what we learned.


## Slide 3: The game in 30 seconds (35 s)

[Baya Chaabene] The game in thirty seconds. Each player is a Pac-Man. A small dot gives ten points. A big power pellet gives fifty points and five seconds of power. While you have power, touching another player sends them back to their start and costs them fifty points. A game lasts sixty seconds and the highest score wins. On the right of the screen you see the scores, and in the corner the network numbers we will talk about later.


## Slide 4: One server, three players (30 s)

[Baya Chaabene] One laptop runs the server, three laptops are players. The golden rule: the server decides everything. A player only sends a direction, called INPUT. Ten times per second the server moves everybody, counts the points and sends the whole game, called STATE, to all players. Players only draw what they receive. So all screens show the same game, and nobody can cheat by changing the score on their own laptop.

> Likely question: Why send the whole game instead of only the changes?
> Answer: If one STATE is lost, the next one is complete again, so UDP can simply skip a lost one.

## Slide 5: A game, message by message (35 s)

[Baya Chaabene] This is one game, message by message. A player logs in with a name, creates or joins a room, and presses R when ready. When everyone is ready the server sends GAME_START with the maze and the colors. Then for sixty seconds the players send INPUT and the server sends STATE, six hundred times. At the end GAME_OVER gives the ranking. Every message is a small JSON object, and the messages are identical on TCP and UDP.


## Slide 6: Same game, only the transport changes (30 s)

[Baya Chaabene] To compare fairly, everything that is not networking is written once, in the common folder: the rules, the lobby and rooms, the game loop and the message format. The TCP folder and the UDP folder only move bytes. One test even checks that both versions deliver exactly the same messages. So any difference you see today comes from the network, not from the game. Now [Mohamed Aziz Souissi] presents the TCP version.

> Likely question: How do you know both versions behave the same?
> Answer: A parity test plays the same session on TCP and UDP and checks that the messages are identical; 118 automated tests in total.

## Slide 7: TCP: one connection per player (35 s)

[Mohamed Aziz Souissi] TCP works like a phone call: you connect first, then you talk. The server opens a listening socket on port 5050. For each player, accept gives a new socket, just for that player, and we start two threads: a reader that receives and a writer that sends from a queue. So one slow player never blocks the others. TCP does a lot for us: it resends lost data and keeps everything in order.

> Likely question: Why a writer thread and not just send()?
> Answer: send() can block if a client is slow; with a queue per client the game thread never waits.
>
> Likely question: Why TCP_NODELAY?
> Answer: Without it TCP may hold small messages to group them, which delays our 10 STATEs per second.

## Slide 8: TCP delivers bytes, not messages (35 s)

[Mohamed Aziz Souissi] The tricky part of TCP: it delivers a stream of bytes, not messages. One recv can return half a message, or three messages glued together. Here the first recv ends in the middle of the word PING. Our fix: every message is one line of JSON ending with a newline. We keep a buffer and only cut at newlines. We tested messages split in two, merged, and even one byte at a time.


## Slide 9: UDP: one socket for everyone (35 s)

[Mohamed Aziz Souissi] UDP works like sending postcards: there is no connection, every packet travels alone. The server has one single socket for all players and reads it in one loop. Each packet carries the sender's address, so we keep a table from address to player. One packet is one message, so no cutting is needed. But nothing is guaranteed: a packet can be lost, arrive twice, or arrive out of order. That is our job now.


## Slide 10: Lost packets: we built our own safety net (35 s)

[Mohamed Aziz Souissi] So we built our own safety net. Every important message gets a number, here JOIN number 7. The receiver answers ACK 7: got it. If no ACK comes back within 200 milliseconds, the sender sends it again, up to fifteen times. If a copy arrives twice, the receiver sees the same number and ignores it, and messages are delivered in order. Our tests at 30 percent loss check that every important message arrives exactly once and in order.

> Likely question: What if the ACK is lost instead?
> Answer: The sender resends; the receiver sees #7 again, ignores the copy and ACKs again.
>
> Likely question: What if all 15 resends fail?
> Answer: The message is given up and the 4 s heartbeat removes that player. At 30 % loss, 0 were given up.

## Slide 11: Not every message has to arrive (35 s)

[Mohamed Aziz Souissi] The key idea of our UDP version: not every message has to arrive. Lobby messages and game events must arrive, so they use our safety net. But STATE, the picture of the game, is sent ten times per second. If one is lost, the next one arrives 100 milliseconds later and is complete. Resending the old one would only add delay. So STATE, INPUT and PING are sent once and never resent. TCP cannot make this choice: it resends everything.


## Slide 12: When a player disappears (45 s)

[Mohamed Aziz Souissi] Last design question: what if a player disappears? If the game program crashes on a TCP laptop, its operating system closes the connection for it, so the server knows almost immediately: we measured 0⁠–⁠95 ms. With UDP there is no connection to close, so the only signal is silence: after 4 seconds without any packet, the player is removed. If the Wi-Fi goes off, even TCP gets nothing, so we added a heartbeat: every player sends a PING each second. In every case the others see that the player left, and the game goes on. Now [Yahia Mahfoudh] shows all of this live.

> Likely question: Why not a shorter UDP timeout?
> Answer: At 30 % loss several PINGs in a row can be lost; 4 s avoids kicking players who are still there.

## Slide 13: Live demo: 4 games on 4 laptops (40 s)

[Yahia Mahfoudh] Now the live demo. We play four short games, and each one proves something. Games 1 and 2: a normal game on TCP and on UDP, and in each one we crash a player on purpose. Game 3: UDP with 30 percent of the packets thrown away. Game 4: a player's Wi-Fi goes off. I run the server; its log is on the projector so you can see every event with its time.

## Slide 15: UDP: the same game, then a crash (100 s)

[Yahia Mahfoudh] Game 2, the same game over UDP. The log now says NEW PEER instead of CONNECT: there is no connection, the server just sees packets from a new address. The corner shows lost zero percent of updates on our network. At forty seconds left we kill carol again. This time nothing happens at first: carol's laptop has nothing to close. Count with me: after about four seconds of silence the server removes carol.


## Slide 16: UDP with 30 % packet loss (110 s)

[Yahia Mahfoudh] Game 3: we now throw away thirty percent of all packets on purpose, on the server and on every player. Login, joining the room and ready still work: these messages use our safety net and are resent. In the corner you see about thirty percent of updates lost. The players jump a bit, but the game never stops, because we never wait for an old picture. When the game ends I stop the server: its statistics show the resends, and zero messages given up.


## Slide 17: TCP: Wi-Fi off in the middle of a game (100 s)

[Yahia Mahfoudh] Game 4, back to TCP. At forty seconds left, bob turns the Wi-Fi off but keeps the game open. Now there is no crash, so no operating system closes anything: TCP alone would wait for minutes. On the other screens bob stops moving, and about five seconds later the server says bob left, thanks to our heartbeat. bob's own window says the server is silent. The game goes on for alice and carol.


## Slide 18: If we have time (skip if late)

[Yahia Mahfoudh] Only if we are ahead of time. First, TCP with thirty percent loss, made by the operating system: the game freezes and then jumps, because one lost packet holds back everything behind it. Second, a player on a phone hotspot joins through our Cloudflare tunnel. Otherwise we skip this slide.


## Slide 19: Under loss, TCP waits and UDP doesn't (30 s)

[Yassine Friaa] Now our measurements. We ran three bots for two minutes, with zero, ten and thirty percent of packets lost on purpose. This chart is the round-trip time. Without loss both are under one millisecond. With loss, TCP waits: when one packet is lost, everything behind it waits until it is resent. That is called head-of-line blocking. At thirty percent loss TCP needs 199 ms; UDP stays at 0.9 ms, because it never waits.

> Likely question: Why is the loss made differently for TCP?
> Answer: TCP must see real lost segments to resend them, so the kernel drops them; our --drop option only exists in the UDP code. Same rates, different method.
>
> Likely question: Why measure on one Mac?
> Answer: It removes Wi-Fi noise, so the only difference is the loss we add on purpose.

## Slide 20: UDP skips lost updates, TCP freezes (30 s)

[Yassine Friaa] The other side of the story. Left: TCP never loses an update, zero percent at any loss. UDP skips the lost ones: about ten and thirty percent, exactly the loss we added. Right: freezes, moments of more than a quarter second without a new picture. TCP freezes much more often, because it waits for every lost packet. So for a live game, skipping an old picture is better than waiting for it.


## Slide 21: How fast a crashed player is noticed (25 s)

[Yassine Friaa] How fast is a crashed player noticed? With TCP, 0⁠–⁠95 ms: the operating system closes the connection. With UDP, 4.0⁠–⁠4.5 s: we have to wait for four seconds of silence. This is the price of having no connection. And our safety net works: at thirty percent loss, the important messages that were lost were resent, and none was given up.


## Slide 22: Who wins? It depends on the message (35 s)

[Yassine Friaa] So which one is better? It depends on the message. TCP is best when everything must arrive: the lobby, the rooms, the results. It is simple, notices crashes immediately and passes firewalls easily. UDP is best for the live game when packets are lost, because it never waits for an old picture, but we had to build reliability ourselves. Real online games do what we did: UDP for live data, plus a small reliable layer for the rest.

> Likely question: If you started again, which one would you choose?
> Answer: UDP for the game data and our reliable layer for the lobby, like we did, because the game only needs the newest STATE.

## Slide 23: What was hard (35 s)

[Yassine Friaa] What was hard? With TCP, understanding that one recv is not one message. With UDP, building sequence numbers, ACKs and resends ourselves, and testing them under loss. For both, choosing the timeout: too short and players on bad Wi-Fi get kicked, too long and a dead player stays in the game. And real networks: firewalls, and campus Wi-Fi that blocks laptops from talking to each other. That is why we check the network with a small tool before playing.

> Likely question: What happens if STATE grows past the safe UDP size?
> Answer: IP would split the packet and losing one piece loses the whole STATE. Ours is 1228 bytes, under the ~1472-byte limit; we warn above 1200.

## Slide 24: Bonus: players on different networks (30 s)

[Yassine Friaa] The bonus: players on different networks. Routers block connections that come in from outside, and we cannot change campus or hotspot routers. So the server dials out. For TCP a Cloudflare tunnel carries the traffic from a remote player to our server. Cloudflare does not carry UDP, so for UDP we use a relay called playit. The TCP path works; the UDP tunnel is not set up yet.

> Likely question: Why not just open port 5050 on the router?
> Answer: We do not control campus or hotspot routers, and many use carrier NAT; an outgoing tunnel works everywhere.

## Slide 25: What we take away (25 s)

[Yassine Friaa] To conclude. TCP is reliable and simple, but one lost packet makes everything wait. UDP never gets stuck on an old packet, but we have to decide ourselves what to resend. For a live game, UDP with a small reliable layer gives the best of both. Thank you, we are happy to answer your questions.
