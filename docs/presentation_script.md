## Slide 1: Maze Arena (60 s)

[Presenter 1] Hello, we are [Name 1], [Name 2], [Name 3] and [Name 4]. Our project is Maze Arena, a small multiplayer maze game where up to three players race to eat pellets. We built the same game twice: once over TCP and once over UDP, so we can compare the two protocols on the same workload. The design is simple. One computer runs the server, three computers run a client. The server is authoritative: it alone moves the players and decides who scores, ten times per second. A client sends only a direction, and the server sends the full game state, called STATE, to everyone after each step. The rules live once in the common folder, and both servers use the same code, so any difference we measure comes from the network, not from the game.

> Likely question: Why an authoritative server?
> Answer: Clients cannot cheat or disagree: only the server changes the game, and every client draws the same STATE.
>
> Likely question: Why send the full STATE instead of changes?
> Answer: If one STATE is lost, the next one is complete again, so UDP can simply skip a lost one.

## Slide 2: TCP version: one connection per player (50 s)

[Presenter 2] Here is the TCP version. The server opens one listening socket on port 5050. Each time a player connects, accept gives us a new socket just for that player, and we start two threads for it: a reader that receives, and a writer that sends from a queue, so one slow player never blocks the others. TCP is reliable and ordered, but it is a byte stream: it has no message edges. One recv can return half a message or three messages. So we end every JSON message with a newline and keep a buffer until we see one. The message flow is: LOGIN, then the lobby and rooms, GAME_START, then INPUT and STATE ten times per second, and GAME_OVER.

> Likely question: Why a writer thread and not just send()?
> Answer: send() can block if a client is slow; with a queue per client the game thread never waits.
>
> Likely question: Why TCP_NODELAY?
> Answer: Without it TCP may hold small messages to batch them, which adds delay to our 10 STATEs per second.

## Slide 3: UDP version: one socket, our own reliability (55 s)

[Presenter 2] Now UDP. There is no connection: the server has one socket for all players and reads it in one loop. Each datagram comes with the sender's IP and port, so we keep a map from (ip, port) to the player's session. One datagram is one message, but UDP may lose, duplicate or reorder it. Important ones, like JOIN or GAME_OVER, get a sequence number; the receiver answers with an ACK, and the sender resends every 200 milliseconds until it gets it, up to 15 times. Look at the timeline: the first JOIN is lost, it is sent again 200 milliseconds later, and the ACK comes back. Duplicates are dropped by seq. STATE, INPUT and PING are never resent: a new STATE comes 100 milliseconds later anyway, and old ticks are thrown away.

> Likely question: What if the ACK is lost instead?
> Answer: The sender resends; the receiver sees seq 7 again, drops the duplicate, and ACKs again.
>
> Likely question: What if all 15 resends fail?
> Answer: The message is given up and the 4 s heartbeat removes that player. In our 30 % loss test, 0 messages were given up.

## Slide 4: Many players at once, and players who vanish (60 s)

[Presenter 3] How do we handle several players at the same time? TCP gives each player a reader and a writer thread; UDP has one receive loop and a timer thread. In both, the game state is protected by one lock. Now disconnections. With TCP, if a client program crashes, its operating system closes the connection, and we saw it in 0⁠–⁠95 ms. But if the Wi-Fi goes off, nothing is sent at all, so TCP alone would wait for minutes: our watchdog drops a silent player after 5 seconds. UDP has no connection, so silence is the only signal: after 4 seconds without a datagram the player is removed; we measured 4.0⁠–⁠4.5 s. Either way the others get PLAYER_LEFT and keep playing, and if only one player is left, the game ends. Our chaos test never crashed either server.

> Likely question: Why not a shorter UDP timeout?
> Answer: Under 30 % loss several PINGs in a row can be lost; 4 s avoids kicking players who are still there.
>
> Likely question: Can two threads move a player at the same time?
> Answer: No. Every change to the game goes through the same lock.

## Slide 5: Our measurements: TCP waits, UDP skips (55 s)

[Presenter 3] These are our own numbers, from metrics slash results dot csv. Three bots, 120-second games on one Mac, at 0, 10 and 30 percent loss. Left chart: round-trip time. Without loss both are under 1 millisecond. With loss, TCP waits for every lost packet to be resent, and all later data waits behind it: that is head-of-line blocking. Its RTT grows to 30 ms and then 199 ms. UDP stays at about 0.9 ms, because nothing waits. Middle: TCP never loses a STATE; UDP simply skips the lost ones. Right: TCP freezes for more than a quarter second much more often. One honest caveat: TCP loss is applied by the kernel, UDP loss by our drop option, at the same rates. LAN and internet numbers we measure live today.

> Likely question: Why is TCP loss done differently?
> Answer: TCP must see real lost segments to resend them, so the kernel drops them; our --drop option only exists in the UDP code. Same rates, different method.
>
> Likely question: Why measure on loopback?
> Answer: It removes Wi-Fi noise, so the only difference is the loss we add on purpose.

## Slide 6: What differs, what hurt, who wins (45 s)

[Presenter 4] To sum up the differences: TCP opens a connection and gives us an ordered stream; UDP just sends separate datagrams. With TCP we add the message edges ourselves; with UDP we add reliability ourselves, only for the messages that need it. Friction points: TCP framing; building seq, ACK and resend for UDP; tuning the heartbeat; a 1228-byte STATE close to the safe UDP size; firewalls and Wi-Fi that isolates laptops; and Cloudflare carrying only TCP. So where did each protocol win? TCP for the lobby and results, where everything must arrive, and it passes firewalls easily. UDP for live play under loss: its round-trip time stayed flat.

> Likely question: If you started again, which one would you choose?
> Answer: UDP for the game data and our reliable layer for the lobby, like we did, because the game only needs the newest STATE.
>
> Likely question: What happens if STATE grows past the safe size?
> Answer: IP would split the datagram; losing one piece loses the whole STATE. We warn above 1200 bytes; a fix would be sending only changes.

## Slide 7: Bonus: players on different networks (60 s)

[Presenter 4] The bonus is to play from different networks, like campus Wi-Fi and two hotspots. Our server sits behind a router with NAT, which blocks connections that come in from outside, and we did not open any port. Instead, the server dials out. For TCP, cloudflared on the server opens a tunnel to Cloudflare. A remote player runs cloudflared access tcp, which gives them a local port; their client connects there, and the traffic goes through Cloudflare's edge to our port 5050. The server sees 127.0.0.1, where the tunnel ends. Cloudflare quick tunnels do not carry UDP, so for UDP we use playit: the player sends datagrams to a public playit address, and the playit agent on our server, through its reverse tunnel, delivers them to the UDP server. Proof: each player shows a different public IP with curl ifconfig.me.

> Likely question: Why not just forward port 5050 on the router?
> Answer: We do not control campus or hotspot routers, and many use carrier NAT; an outgoing tunnel works everywhere.
>
> Likely question: Does the tunnel change the protocol comparison?
> Answer: It adds delay, and playit still carries UDP datagrams, so the TCP vs UDP behaviour stays; we show the internet RTT next to the LAN one.
